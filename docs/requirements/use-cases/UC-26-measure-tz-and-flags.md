## 2. Краткое описание

Два применения одного инструмента. Первое — замер демо-надёжности: четыре запроса замера
(`measure_ask.TZ_QUERIES`: три дословно из ТЗ и один далёкий от датасета домен) прогоняются по нескольку раз без кэша, и измеряется то, что решает
на демо: секунды на запрос против потолка заказчика `DEMO_LIMIT_S = 1200`, число позиций
(ТЗ требует 15) и разброс ТОП между прогонами. Второе — приёмка доработки, живущей за флагом
`WEAK_*` (`weak/flags.py`): правило включения записывается до прогона
(`docs/final-measure.md`), плечи «база / флаг» идут одним прогоном на одном кэше новостей
(`measure_arms_tz.py` на запросах ТЗ, `retro_hits.py --arms` на срезах), и флаг включается на
стенде только при выполненном правиле; не прошёл — остаётся выключенным, а что провалилось,
записывается. Это BR-50 в действии: доработка, меняющая состав или порядок ТОП, не попадает
в выдачу «по ощущению».

## 3. Предусловия

- Корпус (UC-20/UC-22) и шарды (UC-21) наполнены; сервер моделей запущен с `LLM_MODEL` и
  `EMBEDDING_MODEL`; замок `runner.MODEL_LOCK` свободен (очередь стенда пуста — замер держит
  замок часами).
- `pip install -e ".[dev,ml]"`; `pytest` зелёный (`docs/final-measure.md` §0).
- Для плеч с `WEAK_EXTRA_SOURCES` — сеть до NIH RePORTER, Europe PMC, ClinicalTrials.gov и
  каталога YC; для плеч без слоёв — ключи EPO (иначе патенты пропускаются с пометкой).
- Для приёмки плеча `final` — ручная разметка карточек для судьи (`scripts/precision_pairs.tsv`,
  UC-23 A1) и независимый судья по `LLM_BASE_URL`.
- Кэш живого поиска включён на время плеч (`measure_arms_tz.py` ставит `cache.ENABLED = True`
  сам); плечи одного запроса идут подряд, пока кэш (24 ч) жив.

## 4. Триггер

Правка, влияющая на состав или порядок ТОП либо на время прогона (общий DoD в 08 §4.2 и
UC-03 требует строку в `reports/ask-tz.tsv`); новая доработка по консультации 16.10,
заведённая за флагом; подготовка демо; перемер после исправлений ревью (`OQ-11`).

## 5. Основной поток

1. ML-инженер записывает правило включения ДО прогона в `docs/final-measure.md` — общее
   (ретро-тест: «в ТОП или наблюдать» и «в ТОП-15» не меньше базы; датасет заказчика: не
   меняется по построению, `measure_signal_kinds.py` флагов не читает; живые запросы ТЗ:
   карточек-категорий и Big Tech-направлений с продажами в ТОП меньше, чем в базе) и своё у
   каждого флага (`WEAK_ONPOINT_COMPANIES` — нет ASUS/UGREEN/D-Link в «технологиях в ИИ»;
   `WEAK_LAYERS` — трансформеры на срезе 2017-12-01 не в «уже тренд»; `WEAK_TECHNIQUE` —
   снимает не больше трети ТОП; `WEAK_EXTRA_SOURCES` — грант, препринт или испытание хотя бы у
   трети строк биотеха и энергетики). Список категорий `measure_arms_tz.CATEGORIES` и состав
   плеч `retro_hits.ARMS` фиксируются; новое правило — новые плечи и свои папки (`base2`,
   `extra-layers3`, `base4`, `final`), чтобы не смешать с прогонами старого правила.
2. ML-инженер прогоняет `pytest` и запускает плечи на запросах ТЗ одним вызовом:
   ```bash
   python scripts/measure_arms_tz.py --arms base4,final --reps 2
   ```
3. Система под замком `model` для каждого запроса `TZ_QUERIES` и каждого плеча вызывает
   `retro_hits.set_arm` (ставит атрибуты `weak.flags` в памяти процесса: `LAYERS`,
   `TECHNIQUE`, `ONPOINT_COMPANIES`, `EXTRA_SOURCES`, `BURST`), выполняет `ask.run` и пишет
   `reports/arms-tz/<плечо>[-rN]/<запрос>.json`. Готовый JSON пропускается — оборванный прогон
   продолжается тем же вызовом. В таблицу `reports` стенда плечи не пишутся: экспериментальные
   прогоны не должны попасть в историю интерфейса и в «держится N из K».
4. Система собирает `reports/arms-tz/arms-tz.md`: плечо | запрос | ТОП | наблюдать |
   категорий в ТОП | Big Tech с продажами в ТОП | секунд. Категория — ярлык, после нормализации
   целиком равный термину из `CATEGORIES`; Big Tech с продажами — правило слоя «уже тренд»
   (`weak.layers.big_players` и чтения `commercial_deployment` или `funding_mentioned`).
5. ML-инженер прогоняет те же плечи ретро-тестом (UC-25 A1) и, для плеча `final`, судью
   точности ТОП (UC-23 A1) своей и независимой моделью:
   ```bash
   python scripts/retro_hits.py --arms final            # базы — base, base2
   python scripts/judge_precision.py --dir reports/arms-tz/final
   python scripts/judge_precision.py --dir reports/arms-tz/final --model gigachat3.1-10b-a1.8b
   ```
6. ML-инженер сверяет таблицы с правилом, записанным на шаге 1 (для `final`, §2г: ТОП 15 на
   всех четырёх запросах в обоих повторах; Big Tech с продажами в ТОП не больше наибольшего
   у `base4`; медиана времени не больше `base4`). Разница меньше разброса между повторами
   результатом не считается; правило задним числом не переписывается. У `final` правило по
   времени не выполнено: ≈ +60 с на запрос (медиана ~1150 → ~1214 с, финтех 1234 с, по одному
   прогону на плечо — `docs/todo.md` §117 в корне репозитория, `7ef4aaa`); Big Tech с
   продажами в ТОП 20 → 10, ТОП 15 у обоих.
7. Правило выполнено — ML-инженер включает флаг на стенде: переменная в `.env`
   (`WEAK_LAYERS=1`, `WEAK_EXTRA_SOURCES=1`), `docker compose up -d --build` (флаги читаются
   при импорте `weak.flags` — нужен перезапуск `api`), три примера ТЗ и два запроса вне
   финтеха («биотехнологии», «перспективная энергетика») глазами: приём, подтверждение,
   объяснение, блок «Патенты» (`docs/final-measure.md` §4). Не выполнено — флаг остаётся
   выключенным, в протоколе записано, что именно провалилось; статус FEAT-14 — «за флагом».
   Исключение — решение владельца продукта включить флаг, не прошедший правило: оно
   записывается с тем, какое условие правила не выполнено и почему принято (протокол
   `docs/todo.md`, техдока §10). Так включены `WEAK_LAYERS=1` и `WEAK_EXTRA_SOURCES=1`
   (плечо `final`): время сверх `base4` владелец принял («главное качество»). Правило §2г при
   этом не переписывается; остальные флаги на стенде выключены.
8. ML-инженер замеряет демо-надёжность итоговой конфигурации стенда:
   ```bash
   python scripts/measure_ask.py --tz --repeat 3
   ```
9. Система для каждого из четырёх запросов делает `--repeat` прогонов подряд без кэша; каждый
   прогон пишет в таблицу `reports` как `tz-<запрос>-<YYYYmmdd-HHMMSS>` (и копией в
   `reports/ask/`) — туда же, куда пишут веб и очередь, с пометкой «держится N из K» по
   прошлым прогонам того же запроса; после каждого прогона переписывает сводку
   `reports/ask-tz.tsv` (`TZ_COLUMNS`); печатает долю срабатывания каждой проверки
   уверенности (выше `CHECK_CEILING = 0.9` — пометка «⚠️ не различает»; замену проверки
   делает человек по этому выводу — BR-51, ручная проверка), попарное пересечение ТОП
   между прогонами (дословно, Жаккар, по направлению через `history.overlap`) и итог: медиана и
   максимум секунд против `DEMO_LIMIT_S`, медиана и минимум размера ТОП.
10. ML-инженер переносит числа в 01-vision §7 и техдоку §10 (время, полный ТОП, устойчивость
    повтора), а вердикт по флагам — в техдоку §10 и `02-stakeholders.md` (покрытие STR-14).

## 6. Альтернативные потоки и потоки исключений

**A1. Только замер демо-надёжности** (шаги 8–10 без приёмки). После любой правки конвейера:
`--tz --repeat 3` без кэша — полный разброс вместе с выдачей Google News; `--cached` —
разброс одной модели на тех же источниках (сравним с `--domains`, UC-23 A1). Ночной
последовательный замер — `scripts/night_demo_measure.sh` (A/B подрынков на шести доменах в
одном окне кэша → судья покрытия → ТЗ-запросы без подрынков ×1 → с подрынками ×3), сводка
и вердикт по правилу — `scripts/summarize_demo_measure.py` (подрынки остаются, если покрытие
на `HOLDOUT` не упало, на `TUNE` выросло, медиана ТОП выросла и медиана секунд меньше
`DEMO_LIMIT_S`; решение принимает человек, глядя на карточки).

**A2. Нулевой контроль плеч** (шаг 2) — `--reps N`: N повторов каждого плеча в папках
`<плечо>-r1…rN` на одном кэше — разброс самой системы. Правило §2в для `extra-layers3`:
ТОП 15 во всех повторах; наибольшая сумма Big Tech с продажами по повторам флага меньше
наименьшей по повторам `base2`; медиана времени не больше `base2` плюс 120 с.

**A3. Направления из всплеска** (`WEAK_BURST`, плечи `burst`, `burst-only`; шаги 2, 5):
```bash
python scripts/measure_retro_reach.py                       # досягаемость, без модели
python scripts/retro_hits.py --domain ИИ --arms base,burst,burst-only
python scripts/measure_arms_tz.py --arms base,burst,burst-only
```
Правило §2а: до пула кандидатов доходят не меньше двух строк ИИ из 14 хотя бы в одном плече
всплеска (база — 0); ТОП 15 на всех четырёх запросах и Big Tech с продажами меньше базы;
медиана времени не больше базы плюс 120 с. `burst-only` — честное плечо ретро-теста
(направления модели на срезе знают будущее). Базовая линия: в финал всплеск не идёт.

**A4. Пересчёт таблиц без прогона** (шаги 3–4) — `--report-only` по готовым JSON; у
`retro_hits.py` так же, `--fresh` перезапускает.

**A5. Локальная модель против облачной** (`docs/final-measure.md` §3) — UC-23 A6; в правило
включения флагов не входит.

**E1. Замок модели занят** (шаги 3, 9). `locks.Busy`: `measure_ask.py` и `measure_arms_tz.py`
печатают «занято: …» и выходят кодом 75 (NFR-26); прогон не ждёт и ничего не пишет.

**E2. Кэш новостей истёк между плечами** (шаг 3). Плечи сравнивали бы разные наборы новостей;
прогон запроса повторяется всеми плечами одним вызовом (удалить JSON запроса).

**E3. Прогон вышел за потолок или ТОП короче 15** (шаг 9). Не отказ скрипта, а результат:
строка в `ask-tz.tsv`; для приёмки флага — правило «ТОП 15 на всех четырёх» провалено.

**E4. Разница между плечами меньше разброса** (шаг 6). Например, 2 против 3 строк в ретро-тесте
вне ИИ одним прогоном: нулевой контроль (A2) показывает, различимы ли такие разности; правило
остаётся как записано, вердикт — «не показано» (`OQ-17`).

**E5. Отказ источника внутри плеча** (шаг 3). Как в UC-03: источник в `live_errors`, прогон
продолжается; у опциональных источников отказ — «не проверено», а не «ничего нет» (иначе
слой «наблюдать» получал бы кандидатов за сбой чужого API).

## 7. Постусловия

- Успех: `reports/arms-tz/<плечо>/*.json` и `arms-tz.md`, `reports/retro/<плечо>/retro-hits.md`,
  `judge-precision.tsv/json` для `final`; решение по каждому флагу записано в
  `docs/final-measure.md` и техдоке §10; `.env` стенда отражает решение; `reports/ask-tz.tsv`
  и отчёты `tz-<запрос>-<время старта>` в истории стенда (служебное исключение BR-45). Файлы
  `reports/arms-tz/`, `reports/retro/`, `reports/ask-tz.tsv`, `judge-precision.tsv/json`:
  свидетельство создаётся на машине стенда и в репозиторий не входит (`.gitignore:
  reports/*`); проверка — по имени файла и дате на стенде. Базовая линия: ни один из флагов
  правило не прошёл; `WEAK_LAYERS` и `WEAK_EXTRA_SOURCES` включены на стенде решением
  владельца (исключение из §2г, шаг 7), FEAT-14 «за флагом»; без флагов время 1004–1185 с при
  потолке 1200 с, полный ТОП в 9 прогонах из 12, ≈ 9 позиций из 15 держатся при повторе без
  кэша; для конфигурации стенда эти числа не перемерены.
- Отказ: плечо оборвано — готовые JSON остаются, таблица не переписана; повтор доделывает;
  ни один флаг не включается без таблиц по всем трём правилам (исключение владельца — тоже по
  таблицам, с записью невыполненного условия).

## 8. Особые требования

- BR-07 (ТОП 15 — предмет замера), BR-33 (потолок 1200 с; замер — `measure_ask.py --tz`),
  BR-49, BR-50 (правило до прогона; не прошедшее остаётся выключенным), BR-51 (проверка,
  проходящая у > 90 % пула, заменяется — замер печатает «⚠️ не различает», замену делает
  человек: ручная проверка), BR-13 (отчёты `tz-*` попадают в K прошлых прогонов), BR-45
  (исключение `tz-<slug>-YYYYmmdd-HHMMSS`, время и `started` — старт прогона), BR-52.
- NFR-26 (замок модели), NFR-27 (`DEMO_LIMIT_S = 1200`, `reports/ask-tz.tsv`), NFR-36
  (переменные `WEAK_*` в `.env`), NFR-39, NFR-40 (флаги выключены по умолчанию, включение
  только по протоколу), NFR-44, NFR-61/62 (отчёты `tz-*` — обычные отчёты стенда).
- Плечи сравниваются только внутри одного вызова на одном кэше; плечи из разных дней и
  разных правил несравнимы (отсюда свои папки `base2`, `base4`).
- Правило не переписывается по итогам прогона; включение не прошедшего флага — только как
  записанное исключение владельца продукта (шаг 7), правило при этом остаётся как было.
  Константы правил: `CATEGORIES` — догадка,
  помечена в коде (`measure_arms_tz.py`); «плюс 120 с» — число протокола
  (`docs/final-measure.md` §2а, §2в), в коде его нет и скрипт его не проверяет —
  сравнение медиан времени делает человек по `arms-tz.md`.
- Экспериментальные плечи никогда не пишутся в таблицу `reports`; в историю стенда идут только
  прогоны `--tz` итоговой конфигурации.
- Перед каждым замером: для `--tz` число повторов названо (3 — базовая линия), кэш выключен,
  ожидаемая разница правки больше разброса между повторами (иначе замер не ставится); замок
  модели и окно GPU согласованы — 4 запроса × плечи × повторы × 15–20 мин идут часами, очередь
  стенда на это время пуста; для `final` независимый судья доступен по `LLM_BASE_URL`.
