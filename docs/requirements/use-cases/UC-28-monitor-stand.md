## 2. Краткое описание

Администратор по запросу или по жалобе пользователя определяет состояние стенда: жив ли
исполнитель, что в очереди, чем закончился прогон, какие модели отвечали. Для отказов
читает две строки задания (`error` — что случилось, `error_detail` — сырое исключение) и
выполняет действие по типу отказа. Ценность: любой сбой виден в статусе, а не только в
логе, и у администратора есть процедура на каждый из восьми классов отказа.

## 3. Предусловия

- Стенд развёрнут (UC-27), `api` отвечает на 8010 (локально) или за Funnel.
- У администратора есть доступ к `docker compose` на хосте и к `.env`.
- Сторож (UC-32) запущен вместе с `api`.

## 4. Триггер

Плановая проверка; сообщение Compose о нездоровом сервисе; пользователь прислал
«Подробности» отказа (`error_detail`) по совету из фразы `failure.ADMIN` — «если отказ
повторится, передайте подробности администратору стенда».

## 5. Основной поток

1. Администратор запрашивает здоровье исполнителя:
   ```bash
   curl -s http://127.0.0.1:8010/api/health
   ```
2. Система отвечает 200 `{"status":"ok","worker":true,"last_claim_s":<с>,"restarts":<n>}`:
   `worker` — жив ли поток; `last_claim_s` — секунды с последнего обращения к очереди
   (простаивающий исполнитель обращается каждые `IDLE_POLL_S = 5` с, занятый — молчит на
   время прогона); `restarts` — сколько раз сторож перезапускал поток.
3. Администратор запрашивает очередь:
   ```bash
   curl -s http://127.0.0.1:8010/api/queue
   ```
   Система отвечает списком `[{status, position, mine, created, started, eta_start_s}]` —
   сначала `running`, затем `queued` по порядку id; `id`, `query` и текущая стадия `stage`
   есть только у заданий, поставленных с адреса запроса (`mine: true`, адрес — `BR-36`);
   чужие задания видны без id и текста (`jobs.queue`, `NFR-52`). Администратор с хоста видит
   порядок и ожидаемое начало, но не узнаёт по очереди, чьё и какое задание идёт.
4. Администратор смотрит лог API:
   ```bash
   docker compose logs -f api
   ```
   Система пишет на каждое задание «задание N: старт «…»», «задание N: готово за S с → имя»
   и строку ответа с моделями «ответ «…»: K сигналов, C кандидатов, S источников; модели:
   <роль>=<модель>, …» — роли из `weak/ask.answer_models`: «генерация (локально): …»,
   «эмбеддинги (локально): …», «скоринг (уверенность модели и порядок ТОП): …»
   (`runner.run_query`, `BR-28`, `NFR-38`); `httpx` приглушён до WARNING.
5. При жалобе на отказ администратор открывает задание:
   ```bash
   curl -s http://127.0.0.1:8010/api/jobs/<id>
   ```
   Система отдаёт снимок с `status: failed`, `error` (фраза для пользователя) и
   `error_detail` (`ТипИсключения: текст`); последняя строка `progress` — след стека
   (три кадра, `traceback.format_exc(limit=3)`).
6. Администратор классифицирует отказ по фразе `error` (таблица в §6, A1–A8) и выполняет
   действие.
7. Администратор просит пользователя повторить запрос (кнопка «Повторить запрос» в
   UC-02) или сам ставит его через `POST /api/ask`.
8. Администратор убеждается по `/api/health` и логу, что прогон идёт: `worker: true`,
   строки «задание N: старт».

## 6. Альтернативные потоки и потоки исключений

**Разбор отказов по `failure.explain` (шаг 6).** Фразы `error` и действие администратора:

| # | Фраза `error` (начало) | Тип исключения | Действие |
|---|---|---|---|
| A1 | «Сервер моделей запущен, но модель на нём не загружена, поэтому прогон остановился…» | `LLMError` с текстом из `NO_MODEL` («No models loaded», «model_not_found», «model not found») | Загрузить `LLM_MODEL` и `EMBEDDING_MODEL` в LM Studio; проверить, что сервер на 1234 |
| A2 | «Сервер моделей отклонил запрос, и прогон остановился. Повторите запрос; …» | `LLMError`, текст начинается с `HTTP ` | Прочитать `error_detail`: код ответа LM Studio; проверить `LLM_API_KEY`, версию сервера, контекст модели |
| A3 | «Модель ответила не по схеме, и прогон остановился. Повторите запрос: такой сбой обычно разовый.» | иной `LLMError` (нарушение JSON-схемы) | Повтор; при повторении — проверить, что загружена именно `google/gemma-4-12b-qat` (structured output, `NFR-47`) |
| A4 | «Стенд не достучался до сервера моделей или поиска по корпусу, и прогон остановился…» | `httpx.ConnectError`, `httpx.ConnectTimeout` | Проверить LM Studio (1234) и шард-сервер (8020, `GET /health`); `host.docker.internal` из контейнера |
| A5 | «Сервис стенда не ответил вовремя, и прогон остановился…» | `httpx.TimeoutException` | Проверить загрузку GPU и `LLM_TIMEOUT_S` (180 с); нет ли параллельного потребителя модели (докачка векторов, замеры держат `MODEL_LOCK`) |
| A6 | «Сервис стенда ответил ошибкой, и прогон остановился…» | иной `httpx.HTTPError` | Прочитать `error_detail`: какой сервис и код; живые источники сами по себе прогон не роняют (`NFR-20`) — это модели или шард-сервер |
| A7 | «База данных стенда недоступна, и прогон остановился…» | `psycopg.OperationalError` | `docker compose ps postgres`, `docker compose logs postgres`; исполнитель переподключается сам через `RECONNECT_S = 5` с (`NFR-18`) |
| A8 | «Прогон остановился на внутренней ошибке. Повторите запрос; …» | любое иное исключение, `SystemExit` | Прочитать след стека в последней строке `progress`; завести дефект; поток исполнителя жив (`test_system_exit_in_runner_fails_job_and_keeps_worker`) |

Отдельная фраза сторожа: «прогресс не двигался N с — задание снято сторожем» (`BR-41`) —
поток, повисший на сетевом вызове, не освобождён; см. A10.

**A9. `/api/health` отвечает 503 (шаг 2).** Тело `{"status":"down", "worker": false|true,
"last_claim_s": …, "restarts": …}`. Два случая: `worker: false` — поток мёртв, сторож
перезапустит его в пределах `WATCHDOG_S = 60` с и увеличит `restarts`; `worker: true` при
`last_claim_s > STUCK_RUNS × typical_run_s` — исполнитель занят дольше двух типичных
прогонов (зависший сетевой вызов). Compose считает сервис unhealthy после 3 неудачных
проверок по 60 с, но с `restart: unless-stopped` сам контейнер не перезапускает (политика
реагирует на выход процесса, не на healthcheck).

**A10. Зависший исполнитель (после A9 с `worker: true`).** Сторож пометит задание `failed`
(«прогресс не двигался…»), но поток остаётся занят. Администратор перезапускает контейнер:
```bash
docker compose restart api
```
Очередь в Postgres переживает перезапуск (`NFR-17`); задания `running` возвращаются в
голову очереди с удалением событий (`BR-40`), прогон начинается заново; `running` с флагом
`cancel` (автор просил отмену) становится `cancelled`, а не возвращается
(`jobs.requeue_stale`); ожидающие не теряют места.

**A11. Очередь растёт, а прогон идёт (шаг 3).** Нормально: один исполнитель (`BR-34`),
каждый ожидающий видит место и ожидаемое начало (UC-02). Если один адрес занял три слота
(`MAX_ACTIVE_PER_CLIENT = 3`) ошибочными запросами, снять их может только автор — с того
же адреса, `POST /api/jobs/{id}/cancel` (кнопка «Отменить» на экране ожидания, UC-02): ожидающее → `cancelled` сразу, идущее получает флаг `cancel` и снимается на границе
стадии; с чужого адреса — 403, нет задания — 404 (`FEAT-41`). Отдельной отмены
администратору нет: ему остаётся попросить автора отменить или ждать; перезапуск `api`
заданий не удаляет — идущее без флага `cancel` возвращается в очередь.

**A12. Пользователь прислал `error_detail` без id задания.** По `GET /api/queue` чужое
задание не найти (id и текст только у своих, шаг 3). Администратор находит его по логу:
`docker compose logs api | grep "задание"` — строки «задание N: старт «…»» и «задание N:
отказ» связывают id с текстом запроса; история отчётов отказы не содержит — только готовые.

**E1. `api` не отвечает вовсе (шаг 1).** `docker compose ps` → контейнер не `running`;
`docker compose logs api` — причина (чаще: Postgres не healthy, см. UC-27 E2).
`docker compose up -d api`.

**E2. Лог не содержит строки с моделями после «готово» (шаг 4).** Строка пишется
`runner.run_query` после прогона; её отсутствие при `done` означает запуск через иной
runner (тесты, скрипты) — проверить, что `api` запущен `_default_app` с `run_query`.

## 7. Постусловия

**Успех.** Администратор знает состояние исполнителя, содержимое очереди, причину каждого
отказа и выполнил действие по таблице; стенд принимает и выполняет запросы; `restarts`
и 503 объяснены.

**Отказ.** Причина отказа не определяется по `error`/`error_detail` — заводится дефект с
копией `error_detail` и следа стека из `progress`.

## 8. Особые требования

- `FEAT-36` (эксплуатация: `/api/health`, `/api/queue`, логи, сторож), `FEAT-41` (отмена
  своего задания автором — A11).
- `BR-41` (снятие зависшего задания), `BR-42` (две строки отказа, RFC 9457), `BR-43`
  (сбой записи события не роняет прогон — в логе остаётся предупреждение «событие … не
  записалось»), `BR-47` (события хранятся только у идущих и последних `jobs.HISTORY = 20`
  готовых; сторож чистит события `done`, `failed` и `cancelled`).
- `NFR-18` (исполнитель не умирает, переподключение `RECONNECT_S = 5` с), `NFR-19`
  (порог сторожа), `NFR-25` (итог задания пишется новым соединением при обрыве),
  `NFR-38` (логи), `NFR-50`/`NFR-51` (доступ к `api` на loopback; через Funnel —
  те же эндпоинты публичны, `OQ-04`).
- Фразы `error` без кода и JSON; сырой текст только в `error_detail` и в последней строке
  `progress`.

## 10. Данные и интерфейсы

| Элемент | Значение |
|---|---|
| `GET /api/health` | 200 `{status:"ok", worker, last_claim_s, restarts}`; 503 `{status:"down", …}` при мёртвом потоке или `last_claim_s > STUCK_RUNS × typical_run_s`; при `runner=None` (тесты) — `{status:"ok", worker:null}` |
| `GET /api/queue` | `[{status, position, mine, created, started, eta_start_s}]`, у своих (`mine`) ещё `id`, `query`, `stage`; `running` первым |
| `GET /api/jobs/{id}` | снимок: `status` (`queued`/`running`/`done`/`failed`/`cancelled`), `progress[]`, `error`, `error_detail`, `report`, `cancel`; 404 «нет такого задания» |
| `POST /api/jobs/{id}/cancel` | только с адреса автора: 200 `{id, status}` (`cancelled` — ожидающее снято; `running` — флаг `cancel`, снимется на границе стадии); 403 — чужой адрес; 404 — нет задания |
| Константы | `api.IDLE_POLL_S = 5`, `api.RECONNECT_S = 5`, `api.WATCHDOG_S = 60`, `api.STUCK_RUNS = 2.0`, `api.POOL_MAX = 8`, `jobs.HISTORY = 20`, `jobs.DEFAULT_RUN_S = 1020`, `jobs.MAX_ACTIVE_PER_CLIENT = 3`, `settings.llm_timeout_s = 180` |
| Фразы отказов | `failure.explain`: 8 ветвей; `failure.RETRY = «Повторите запрос»`, `failure.ADMIN = «если отказ повторится, передайте подробности администратору стенда»` |
| Лог | `docker compose logs -f api`; формат `%(asctime)s %(name)s %(message)s`; логгеры `pelican.api`, `pelican.runner`, `pelican.events` |
| Команды | `docker compose ps`, `docker compose logs -f api`, `docker compose restart api`, `docker compose logs postgres` |
| Код | `src/pelican/api.py` (`health`, `queue`, `job`, `Worker`), `src/pelican/failure.py`, `src/pelican/jobs.py` (`snapshot`, `queue`, `fail`, `typical_run_s`), `src/pelican/runner.py` |
