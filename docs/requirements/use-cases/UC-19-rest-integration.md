## 2. Краткое описание

Интегрирующая система или скрипт без интерфейса ставит запрос на поиск слабых сигналов,
следит за его выполнением по курсору событий, забирает готовый результат как JSON,
снимает своё ненужное задание, видит очередь, ищет по истории и получает словарь подсказок,
чтобы объяснять числа теми же словами, что интерфейс. Ценность — та же выдача, что у
аналитика в браузере, но машиночитаемая и встраиваемая. Перечень маршрутов — §10 (сверен с
`api.py`); коды и строки ошибок — `06-supplementary-spec.md` §7.1.

## 3. Предусловия

- Стенд развёрнут (UC-27): `api` отвечает на `GET /api/health` кодом 200.
- Потребитель достигает адреса API: внутри сети Compose (`http://api:8010`), на хосте
  (`http://127.0.0.1:8010`) или через Funnel (`https://<узел>/api/...`).
- Потребитель умеет читать JSON и повторять опрос с задержкой.

## 4. Триггер

Потребителю нужен ТОП-15 по направлению или данные прошлого прогона.

## 5. Основной поток

1. Потребитель отправляет `POST /api/ask` с телом `{"query": "<направление>"}` и
   заголовком `Content-Type: application/json; charset=utf-8`.
2. Система схлопывает пробелы, проверяет длину (не меньше 3 символов, `api.ask`), ищет
   готовый отчёт того же запроса версии не ниже `weak/ask.REPORT_VERSION` и активное
   задание с тем же текстом; ничего не найдя, ставит задание в очередь под адресом клиента
   (`api._client`) и будит исполнителя.
3. Система отвечает **202** со снимком задания: `id`, `status: "queued"`, `position`,
   `eta_start_s`, `typical_run_s`.
4. Потребитель опрашивает `GET /api/jobs/{id}/events?after=<next>` не чаще раза в 2,5 с
   (как веб-интерфейс, `web/src/lib/live.js POLL_MS`), начиная с `after=0`, и каждый
   раз берёт `next` из ответа как следующий курсор.
5. Система отдаёт `status`, `elapsed`, `next` и события после курсора; вид события — в
   поле `t` (`stage`, `facets`, `counts`, `verdict`, `relevance`, `top`, `patents`,
   `card`, `titles`, `done`, `failed`), обязательные поля — по контракту
   `src/pelican/events.py` (UC-03 §10). Своего события у отмены нет: снятое задание видно
   по `status: "cancelled"` (A7).
6. Когда в ответе `status: "done"` (и пришло событие `done` с именем отчёта), потребитель
   запрашивает `GET /api/reports/{report}`.
7. Система отдаёт результат целиком: JSON `AskResult` с `signals`, `thin`, `excluded`,
   `facets`, `sources_processed`, `candidates`, `models`, `live_errors`, `version` и
   прочими полями (структура — `src/pelican/weak/ask.py AskResult`, `weak/page.to_json`).
8. Потребитель, который показывает числа и источники человеку, запрашивает
   `GET /api/glossary` и использует `hints` и `live_names`, чтобы подписать их теми же
   словами, что интерфейс; потребитель, обрабатывающий JSON машинно, этот шаг пропускает.

## 6. Альтернативные потоки и потоки исключений

**A1. Готовый отчёт (шаг 2).** По запросу уже есть отчёт версии ≥ `REPORT_VERSION`:
система отвечает **200** `{status: "done", query, report, cached: true}`; потребитель
переходит к шагу 6 с этим именем. Регистр запроса не учитывается (`jobs.cached_report`).

**A2. Тот же запрос уже активен (шаг 2).** В очереди или в работе есть задание с тем же
текстом: система отвечает **202** снимком *существующего* задания, дубль не ставится
(`jobs.active_job`, проверка под advisory-блокировкой в `jobs.enqueue`). Потребитель
следит за ним как за своим.

**A3. Снимок без событий (шаг 4).** Потребителю хватает статуса: он опрашивает
`GET /api/jobs/{id}`; у `queued`/`running` ответ несёт `stage_typical` (медиана начала
стадий по последним `jobs.HISTORY = 20` готовым заданиям) и `progress[]` — текстовые
строки «N с · что идёт».

**A4. Поиск истории.** Потребитель вызывает `GET /api/history?limit=&offset=&q=`:
`limit` 1..1000 (по умолчанию 50), `q` — подстрока запроса без учёта регистра; ответ
`{total, items[]}` со сводками (`jobs.summaries`).

**A5 — снято:** маршрут `/r/{name}` убран (`c1c4ea8`); HTML отчёта пишется в
`reports.html`, но наружу не отдаётся — потребитель берёт JSON (шаг 7).

**A6. Повторное открытие по ссылке.** Потребитель, потерявший курсор, начинает с
`after=0`: первая пачка приходит целиком (`jobs.events`), события законченных заданий
хранятся только у последних 20 готовых (`BR-47`), поэтому у старого задания событий может
не быть — потребитель читает отчёт по имени из снимка. Сторож (`jobs.prune_events`)
подрезает события `done`, `failed` и `cancelled`.

**A7. Отмена своего задания.** Потребитель вызывает `POST /api/jobs/{id}/cancel` с того же
адреса, с которого ставил задание (автор — адрес по `BR-36`; аутентификации нет).
Ожидающее → **200** `{id, status: "cancelled"}` сразу, исполнитель его не возьмёт. Идущее →
**200** `{id, status: "running"}`, в снимке `cancel: true`; исполнитель снимает его на
ближайшей границе стадии — на событии `stage`, кроме `save` (`jobs.Cancelled` в
`api.Worker._run`), — и ставит `cancelled`; на стадии `save` отчёт уже посчитан и
сохраняется. Готовое, упавшее и уже снятое не меняются — 200 с текущим статусом. Чужой
адрес — **403** «Задание поставлено с другого адреса — отменить его может только автор.»
(в том числе присоединившийся к чужому заданию по A2 и любой адрес для заданий тем
`topic:<id>`, UC-18 — Прототип); задания нет — **404** «нет такого задания». Отдельной отмены
администратору нет. Снятое задание отчёта не оставляет и освобождает слот лимита (E2);
присоединившиеся к нему по A2 видят тот же `cancelled`.
Если процесс упал, пока идущее задание несло флаг `cancel`, при старте оно становится
`cancelled`, а не возвращается в очередь (`jobs.requeue_stale`, `BR-40`).

**A8. Очередь.** `GET /api/queue` → идущее и ожидающие по порядку: `[{status, position, mine,
created, started, eta_start_s}]`, `position` и `eta_start_s` — как в снимке задания; у своих
(`mine` — адрес совпал с адресом задания) ещё `id`, `query` и `stage` (последнее событие
`stage`), у чужих текста и id нет (`NFR-52`, `jobs.queue`). Без адреса `mine` всегда ложно.

**E1. Запрос короче трёх символов (шаг 2).** **422** «запрос короче трёх символов»
(`BR-37`). Потребитель исправляет запрос.

**E2. Превышен лимит адреса (шаг 2).** У адреса уже `jobs.MAX_ACTIVE_PER_CLIENT = 3`
задания в очереди и в работе: **429** «с вашего адреса уже 3 запроса в очереди и в работе —
дождитесь, пока один из них закончится» (`BR-35`). Потребитель ждёт завершения одного из
своих заданий или снимает ненужное (A7). Адрес — левый `X-Forwarded-For`, иначе адрес
соединения (`BR-36`, `api._client`); прочие заголовки с адресом не читаются, подставной
заголовок лимит не обходит; пустой адрес не ограничен.

**E3. Нет такого задания или отчёта.** **404** «нет такого задания» (`GET /api/jobs/{id}`,
`…/events`, `POST …/cancel`) / «нет такого отчёта» (`GET /api/reports/{name}`; имя вне
формата `BR-45` — тоже 404 до обращения к базе, `jobs.REPORT_NAME`). Потребитель не
повторяет запрос с тем же идентификатором.

**E4. Прогон отказал (шаг 5).** `status: "failed"`, в ответе `error` (фраза для человека
из `failure.explain`) и `error_detail` (сырой текст исключения), событие `failed` с теми же
полями (`BR-42`). Потребитель показывает `error`, `error_detail` передаёт администратору
стенда (UC-28) и, если результат всё ещё нужен, ставит запрос заново тем же `POST /api/ask`:
отказавшее задание отчёта не оставляет, `jobs.cached_report` читает только `reports`, поэтому
повтор создаёт новое задание (или присоединяется к активному, A2).

**E5. Исполнитель мёртв или завис.** `GET /api/health` отвечает **503**
`{status: "down", worker, last_claim_s, restarts}` (поток мёртв или не обращался к очереди
дольше `api.STUCK_RUNS = 2.0` × типичного прогона). Потребитель прекращает ставить
запросы до восстановления (UC-32, UC-28).

**E6. Задание снято сторожем.** `status: "failed"`, `error` = «прогресс не двигался N с —
задание снято сторожем» (`jobs.fail_stuck`, `BR-41`). Потребитель ставит запрос заново.

**E7. Долгое соединение оборвано прокси.** Funnel и спящие вкладки обрывают долгие
соединения, поэтому SSE нет; потребитель всегда опрашивает с курсором (`NFR-30`).

## 7. Постусловия

**Успех.** У потребителя есть имя отчёта и его JSON; отчёт лежит в `reports` бессрочно
(`NFR-58`); повторный `POST /api/ask` с тем же текстом вернёт его из кэша (`BR-38`).

**Отказ.** Задание в состоянии `failed` с `error`/`error_detail`; отчёта нет; лимит адреса
освобождён.

**Отмена (A7).** Задание в состоянии `cancelled`; отчёта нет; лимит адреса освобождён.

## 10. Данные и интерфейсы

- Маршруты (`api.create_app`, полный перечень):

  | Маршрут | Ответы |
  |---|---|
  | `POST /api/ask` | 202 снимок / 200 `cached` / 422 / 429 |
  | `GET /api/health` | 200 / 503 |
  | `GET /api/jobs/{id}` | 200 снимок (+ `stage_typical` у активных) / 404 |
  | `GET /api/jobs/{id}/events?after=` | 200 `{status, report, error, error_detail, elapsed, next, events[]}` / 404 |
  | `POST /api/jobs/{id}/cancel` | 200 `{id, status}` / 403 / 404 |
  | `GET /api/queue` | 200 список (A8) |
  | `GET /api/history?limit=&offset=&q=` | 200 `{total, items[], typical_run_s}` |
  | `GET /api/glossary` | 200 `{hints, live_names}` |
  | `GET /api/reports/{name}` | 200 `AskResult` / 404 |
  | `GET /api/docs`, `GET /openapi.json` | Swagger и схема (FastAPI) |
  | `/` (статика `_SiteStatic`) | веб-интерфейс, если в `WEB_DIR` есть `index.html`; монтируется последним |

  Других маршрутов нет; коды и точные строки ошибок — `06-supplementary-spec.md` §7.1.
- Тело запроса: `api.AskIn {query: str}`.
- Снимок задания: `jobs.snapshot` — `id, query, status, created, started, finished,
  progress[], error, error_detail, report, cancel, position, eta_start_s`; у активных —
  `typical_run_s`; у `GET /api/jobs/{id}` — ещё `stage_typical`. `status` ∈ {`queued`,
  `running`, `done`, `failed`, `cancelled`} (`schema.sql`); `cancel` — флаг просьбы об
  отмене идущего (A7).
- События: `jobs.events` → `{...data, seq, at, t}`; контракт `events.REQUIRED`, `COUNTS`,
  `RUN_STAGES` (10 стадий, `save` шлёт исполнитель).
- Результат: `AskResult` (`weak/ask.py`), сериализация `weak/page.to_json`; `version` =
  `REPORT_VERSION = 2`.
- Константы: `jobs.MAX_ACTIVE_PER_CLIENT = 3`, `jobs.HISTORY = 20`,
  `jobs.DEFAULT_RUN_S = 1020`, `api.STUCK_RUNS = 2.0`, `api.POOL_MAX = 8`,
  `api.history limit` 1..1000 (50).
- Заголовок адреса: только `X-Forwarded-For` (левый адрес; его перезаписывает Funnel), иначе
  адрес соединения (`api._client`).
