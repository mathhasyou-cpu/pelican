## 2. Краткое описание

Системный сценарий: раз в `WATCHDOG_S = 60` с сторож проверяет, жив ли поток
исполнителя, снимает задание, у которого прогресс не двигался дольше `STUCK_RUNS = 2.0`
× типичного прогона, и обрезает события законченных заданий, оставляя последние
`jobs.HISTORY = 20` готовых. При старте процесса сторожу предшествует возврат брошенных
заданий в голову очереди (брошенное с просьбой автора об отмене снимается в `cancelled`). Ценность: снаружи мёртвый исполнитель неотличим от занятого,
а молча зависший прогресс — от долгого запроса; сторож превращает оба случая в видимый
статус (`/api/health` 503, задание `failed`) и держит таблицу событий компактной.

## 3. Предусловия

- Процесс `api` запущен с `runner` (не тестовый `create_app(..., runner=None)`);
  `Worker.start()` выполнен.
- Postgres доступен; схема применена.

## 4. Триггер

Истечение `WATCHDOG_S = 60` с в потоке `pelican-watchdog` (`self.stop.wait(WATCHDOG_S)`);
при старте процесса — вызов `Worker.start()`.

## 5. Основной поток

1. Время: прошло 60 с с предыдущего обхода; поток сторожа вызывает `Worker.check()`.
2. Система проверяет поток исполнителя: `self.thread.is_alive()`. Жив — переход к шагу 4.
3. Система (поток мёртв и остановка не запрошена): увеличивает `restarts`, пишет в лог
   «исполнитель умер — перезапускаю (N-й раз)», создаёт новый поток `pelican-worker` и
   запускает его. Новый поток переподключается к Postgres и продолжает брать задания.
4. Система открывает соединение и вычисляет порог: `limit = STUCK_RUNS × typical_run_s`,
   где `typical_run_s` — медиана длительности последних `HISTORY = 20` готовых заданий,
   а пока их нет — `DEFAULT_RUN_S = 1020` с (порог 2040 с).
5. Система (`jobs.fail_stuck(conn, limit)`) переводит в `failed` каждое задание `running`,
   у которого `COALESCE(touched, started) < now() − limit`, ставит `finished = now()` и
   `error = «прогресс не двигался N с — задание снято сторожем»` (N = округлённый `limit`);
   `error_detail` остаётся пустым. На каждое снятое задание — строка лога «задание N:
   прогресс стоит дольше S с — снято».
6. Система (`jobs.prune_events(conn)`) удаляет события заданий со статусом `done`, `failed`
   или `cancelled`, кроме последних 20 готовых (`done`, по `finished DESC`); события `queued`
   и `running` не трогаются. Возвращённое число строк не логируется.
7. Сторож засыпает до следующего обхода.

## 6. Альтернативные потоки и потоки исключений

**A1. Старт процесса (вместо шага 1, однократно).** `Worker.start()` до запуска потоков
вызывает `jobs.requeue_stale(conn)`: в одной транзакции переводит `running` с флагом
`cancel` (автор просил отмену) в `cancelled` с `finished = now()` — его события остаются;
затем удаляет `job_events` остальных заданий `running` и переводит их в `queued` с
`started = NULL`, `progress = '[]'`. Исполнитель один, поэтому `running` при старте может
быть только брошенным. В лог — «вернул в очередь
N брошенных заданий». Возвращённое задание оказывается в голове очереди (меньший id) и
прогоняется заново; накопленные события потеряны (`BR-40`, техдока «Ход прогона»).

**A2. Поток жив, но занят дольше порога (шаг 5).** Задание помечено `failed`, пользователь
видит отказ и кнопку повтора (UC-02), но поток исполнителя по-прежнему занят повисшим
сетевым вызовом: `fail_stuck` меняет только строку в базе. Следующие задания ждут, пока
поток не вернётся или администратор не перезапустит контейнер (UC-28 A10). `/api/health`
в это время отвечает 503 `down` по тому же порогу (`last_claim_s > limit`).

**A3. Прогресс идёт редко, но идёт (шаг 5).** `touched` ставит взятие задания (`jobs.claim`:
`status = 'running', started = now(), touched = now()`) и дальше двигает только строка
прогресса `say()` (`jobs.say`: `UPDATE jobs SET progress = …, touched = now()`); событие `emit()`
(`jobs.emit`) лишь вставляет строку в `job_events` и `touched` не трогает. Самое долгое
молчание `say` — проход по шардам, ~3 мин при прогоне ~17 мин (комментарий к `STUCK_RUNS`).
Порог 2 × типичного оставляет запас; задание не снимается.

**A4. Истории готовых заданий ещё нет (шаг 4).** `typical_run_s` возвращает
`DEFAULT_RUN_S = 1020`; порог — 2040 с. Как только набираются готовые задания, порог
следует их медиане (до 20 последних).

**A5. Остановка процесса (шаг 2).** `self.stop` установлен — мёртвый поток не
перезапускается; сторож выходит из цикла.

**E1. Postgres недоступен в момент обхода (шаги 4–6).** `Worker.check()` бросает
исключение; `_watch` ловит его, пишет «сторож: проверка не удалась» и ждёт следующего
обхода. Сторож не падает (`NFR-18`).

**E2. Исполнитель умирает повторно (шаг 3).** Каждый перезапуск увеличивает `restarts`;
значение видно в `/api/health`. Причина — в логе «исполнитель: отказ очереди,
переподключаюсь через 5 с» или в следе исключения; разбор — UC-28.

## 7. Постусловия

**Успех.** Поток исполнителя жив; ни одно задание `running` не старше порога по
`touched`/`started`; `job_events` содержит события только активных заданий и последних
20 готовых (`BR-47`; в коде сверх этого остаются события `cancelled` — DoD «код
расходится»); `/api/health` отражает состояние (`restarts`, 200/503).

**Отказ (обход не удался).** Состояние базы не изменено; следующий обход через 60 с.

## 8. Особые требования

- `FEAT-15` (очередь: устойчивость к перезапуску), `FEAT-18` (сторож снимает зависшее
  задание).
- `BR-34` (один исполнитель — поэтому `running` при старте всегда брошенное), `BR-40`
  (возврат брошенных с потерей событий; с флагом `cancel` — `cancelled`), `BR-41` (текст и порог снятия), `BR-43`
  (сбой записи события не роняет прогон — сторож это не компенсирует, только снимает по
  `touched`), `BR-47` (хранение событий у последних 20 готовых; каскад по FK).
- `NFR-17` (очередь переживает перезапуск), `NFR-18` (перезапуск мёртвого потока,
  `RECONNECT_S = 5` с у самого исполнителя), `NFR-19` (порог снятия, стабильность низкая),
  `NFR-25` (итог задания пишется новым соединением — не сторожем, а `_with_conn`).
- Сторож использует собственное соединение на обход (`jobs.connect`), не пул маршрутов и
  не соединение исполнителя.
- Медиана стадий для полосы ожидания (`jobs.stage_typical`) читает те же последние 20
  готовых — поэтому `prune_events` обязан оставлять ровно их.

## 9. Точки расширения и включения

- Фон для UC-03 (снимает зависший прогон) и UC-28 (объясняет 503 и `restarts`).
- Запускается UC-27 (вместе с `api`).
- Обрезка событий влияет на UC-02: переоткрытие ссылки на законченное задание старше
  20 готовых событий не воспроизводит — экран открывает отчёт.

## 10. Данные и интерфейсы

| Элемент | Значение |
|---|---|
| Таймер | `api.WATCHDOG_S = 60` с, поток `pelican-watchdog` (daemon) |
| Порог снятия | `api.STUCK_RUNS = 2.0` × `jobs.typical_run_s(conn)`; медиана по `jobs.HISTORY = 20` готовым; иначе `jobs.DEFAULT_RUN_S = 17 × 60 = 1020` с |
| Критерий зависания | `status = 'running' AND COALESCE(touched, started) < now() − make_interval(secs => limit)` |
| Запись при снятии | `status = 'failed'`, `finished = now()`, `error = 'прогресс не двигался ' || round(limit) || ' с — задание снято сторожем'` |
| Обрезка | `DELETE FROM job_events WHERE job_id IN (done/failed) AND job_id NOT IN (последние 20 done по finished DESC)` |
| Возврат брошенных | `UPDATE jobs SET status='cancelled', finished=now() WHERE status='running' AND cancel`; `DELETE job_events WHERE job_id IN running`; `UPDATE jobs SET status='queued', started=NULL, progress='[]' WHERE status='running'` — одна транзакция |
| Наблюдаемость | `GET /api/health`: `worker`, `last_claim_s`, `restarts`; 503 при `not alive` или `last_claim_s > limit`; лог `pelican.api` |
| Код | `src/pelican/api.py` (`Worker.__init__`, `start`, `_spawn`, `_watch`, `check`, `alive`), `src/pelican/jobs.py` (`fail_stuck`, `prune_events`, `requeue_stale`, `typical_run_s`; `touched` пишут `claim` и `say`), `src/pelican/schema.sql` (`jobs.touched`, `job_events` FK ON DELETE CASCADE) |

## 11. Открытые вопросы

- `OQ-12` (закрыт, `8361a37`) — снять своё задание может автор (`POST /api/jobs/{id}/cancel`,
  UC-02); без автора задание снимает только сторож, и только по бездействию.
- `OQ-16` — `STUCK_RUNS = 2.0` и `DEFAULT_RUN_S` помечены в коде «догадка»; порог не
  замерен на распределении пауз между строками прогресса.
