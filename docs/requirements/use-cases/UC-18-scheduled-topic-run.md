## 2. Краткое описание

Системный сценарий. Планировщик внутри исполнителя раз в минуту находит активные темы,
у которых подошёл `next_run`, ставит их запрос в очередь особым клиентом, сдвигает `next_run`
на следующую дату и ждёт прогона. После прогона система сравнивает ТОП с прошлым прогоном
темы (появилось / сменило стадию / ушло), пишет строку прогона и, если новых не меньше
порога и у темы включены выпуски, заказывает выпуск-дайджест (UC-16 A2). Ценность: тема
живёт без участия аналитика, а каждая её итерация оставляет проверяемый след.

## 3. Предусловия

- Есть тема с `active = true` и `next_run <= now()` (UC-17).
- Исполнитель запущен (UC-03), планировщик — часть его цикла.
- Для дифа — прошлый прогон темы с отчётом (иначе первый прогон, A1).

## 4. Триггер

Такт планировщика (раз в минуту) в исполнителе `api.Worker` (`IMPLEMENTATION.md`: «цикл в
`Worker` раз в минуту»); либо ручной запуск «Запустить сейчас» (UC-17 A7) — тогда шаги с 3,
без сдвига `next_run` и с пометкой `manual`.

## 5. Основной поток

1. Время: наступает такт планировщика.
2. Система выбирает темы `active AND next_run <= now()`; для каждой — сразу сдвигает
   `next_run` на следующую дату по каденции (неделя / 2 недели / месяц, то же время), чтобы
   долгий прогон не породил второй запуск (BR-54).
3. Система ставит задание напрямую через `jobs.enqueue(query, client = 'topic:<id>')`,
   минуя `api.ask` и его кэш повтора (BR-58); клиент `topic:*` не учитывается в лимите
   «3 с адреса» (BR-35, BR-54); в `claim` такие задания выдаются после ручных (`queued` с
   обычным клиентом идут первыми). Если запрос темы совпадает с активным ручным заданием,
   прогон присоединяется к нему (BR-39, BR-58) — отдельного задания нет, диф считается по
   отчёту того задания.
4. Исполнитель выполняет прогон (include UC-03) — как обычный запрос, без контекста
   углубления; тема получает свежий отчёт, а не кэшированный (BR-58: иначе диф выпуска
   пуст).
5. По готовности отчёта система находит прошлый прогон темы с отчётом и считает диф по
   `Signal.label` между ТОП: `added` — ярлыки, которых не было; `gone` — ярлыки, которых
   нет в новом ТОП (с причиной: класс и `why` из исключённых нового отчёта, если кандидат
   там есть, иначе «не найдено в этом прогоне»; элемент — `{label, title, why}`); `moved` —
   общие ярлыки с изменившейся стадией `{label, from, to}` (сравнение канонических ступеней,
   BR-17). Прототип (`research.js: finishTopic`) пишет `gone` как `{title, why}` с причиной
   всегда «нет в этом прогоне» — §11.
6. Система пишет `topic_runs(topic_id, report, added, moved, gone, started, manual = false)`.
7. Система проверяет условие выпуска: `len(added) >= notify_min AND write_article` (BR-56).
8. Условие выполнено — система ставит задание выпуска (UC-16 A2: задание очереди
   `jobs.kind = 'article'` по BR-57, статья `articles.kind = 'digest'`, `topic_id`,
   `reports = [отчёт прогона]`, диф); по готовности `topic_runs.article_id` заполняется.
9. На странице темы (UC-17 A5) прогон виден с дифом и ссылкой на выпуск; тема показывает
   новый «следующий прогон».

## 6. Альтернативные потоки и потоки исключений

- **A1 (шаг 5). Первый прогон темы.** Прошлого отчёта нет: `added` = весь ТОП, `moved` и
  `gone` пусты, примечание «первый прогон темы»; выпуск не пишется независимо от порога
  (сравнивать не с чем) — исключение записано в BR-56.
  Прототип его не реализует: примечание «первый прогон темы» есть только в данных демо
  (`research-data.js`), а `research.js: finishTopic` у темы без прошлого прогона ставит весь
  ТОП в `added` и при `added ≥ notify` пишет примечание о выпуске — §11.
- **A2 (шаг 7). Новых меньше порога.** `topic_runs` записан без `article_id`; на странице
  темы примечание «статья не писалась: новых сигналов меньше порога (N)».
- **A3 (шаг 7). У темы выключены выпуски.** `write_article = false`: диф записан, выпуск не
  заказывается, примечания нет (KPI темы «статья после прогона: нет»).
- **A4 (триггер). Ручной запуск.** Из UC-17 A7: шаги 3–9 без сдвига `next_run`, `manual =
  true`, на странице темы чип «запущен вручную».
- **A5 (шаг 3). Тема привязана к ветке.** Отчёт прогона получает `thread_id` темы? — нет:
  прогон темы не становится шагом ветки (ветка — цепочка углублений с фокусом); связь только
  через `topics.thread_id` для навигации. Решение по DoR (§11).
- **E1 (шаг 3). Очередь занята ручными запросами.** Задание темы ждёт; `next_run` уже
  сдвинут, второго задания не будет; если ожидание переживает следующий такт, повторной
  постановки нет (условие `next_run <= now()` ложно).
- **E2 (шаг 4). Прогон отказал.** `jobs.failed` с `failure.explain`; `topic_runs` получает
  строку без отчёта и дифа с примечанием «прогон не удался: <фраза>»; выпуск не пишется;
  следующий плановый запуск — по `next_run`.
- **E3 (шаг 8). Выпуск не написан (UC-16 E1/E2).** `topic_runs.article_id` пуст,
  примечание с причиной отказа; диф остаётся.
- **E4 (шаг 2). Тема поставлена на паузу между тактом и прогоном.** Поставленное задание
  выполняется, диф и выпуск пишутся; следующий запуск не планируется. Снять задание нельзя:
  `POST /api/jobs/{id}/cancel` принимает только адрес автора, а автор задания темы —
  `topic:<id>`, поэтому с любого адреса ответ 403 (`jobs.cancel` → `NotAuthor`); отдельной
  отмены администратору нет. Пауза темы задание не снимает.
- **E5 (шаг 1). Исполнитель перезапущен сторожем (UC-32).** Планировщик стартует заново
  вместе с исполнителем; темы с `next_run` в прошлом ставятся на ближайшем такте по одной.

## 7. Постусловия

- **Успех:** новый отчёт в `reports`; строка в `topic_runs` с дифом; `next_run` сдвинут
  (плановый) или не тронут (ручной); при выполнении условия — выпуск в `articles` и ссылка
  в `topic_runs.article_id`.
- **Отказ:** строка `topic_runs` с примечанием об отказе; `next_run` сдвинут; выпуска нет.

## 8. Особые требования

- BR-35, BR-54 (вне лимита адреса; после ручных; сдвиг `next_run` при постановке), BR-56
  (условие выпуска), BR-58 (постановка через `jobs.enqueue`, минуя кэш повтора `api.ask`;
  присоединение к активному ручному заданию по BR-39), BR-57 (выпуск — задание
  `jobs.kind = 'article'`; сама статья — `articles.kind = 'digest'`), BR-40 (брошенное
  задание темы возвращается в очередь как любое; флага `cancel` у него не бывает — E4),
  BR-17 (сравнение стадий), BR-42 (отказ словами пользователя в примечании).
- NFR-17, NFR-18 (планировщик живёт в исполнителе и переживает его перезапуск), NFR-27
  (прогон темы — тот же бюджет 1100 с), NFR-28 (одна модель: темы ≈ 3 ч GPU в неделю при 10
  темах еженедельно — бюджет согласован), NFR-19 (сторож снимает и зависший прогон темы).
- Идемпотентность такта: один такт ставит одну тему не более одного раза; два такта подряд
  не ставят одну тему дважды.

## 10. Данные и интерфейсы

Дельты (`IMPLEMENTATION.md` §6):

- Планировщик: цикл в `api.Worker` раз в минуту (константа, например `SCHEDULER_S = 60`,
  создать): `SELECT … FROM topics WHERE active AND next_run <= now()`; `UPDATE next_run`
  в той же транзакции, что и `enqueue` (или до него).
- `jobs.enqueue(query, client = 'topic:<id>')`: в `enqueue` клиент с префиксом `topic:`
  пропускает проверку лимита; в `claim` — `ORDER BY (client LIKE 'topic:%'), id` (ручные
  первыми).
- Планировщик вызывает `jobs.enqueue` напрямую, а не `api.ask`, поэтому `jobs.cached_report`
  для заданий тем не достигается (BR-58); совпадение с активным ручным заданием —
  `jobs.active_job`, присоединение (BR-39).
- Диф: функция `weak/topics.diff(prev: AskResult, cur: AskResult) -> {added, moved, gone}`
  (создать); сравнение по `label`, стадии через `rubric.STAGES`.
- `topic_runs(topic_id, report, added TEXT[], moved JSONB, gone JSONB, article_id, started,
  manual, note)` — `note` для примечаний («первый прогон темы», «статья не писалась: …»,
  «прогон не удался: …»).
- Снимок задания темы: `client` → подпись ожидания «Прогон темы на автопилоте …».
- Контракт очереди и снимка (требуемое изменение, Прототип): у задания темы `jobs.queue`
  (`GET /api/queue`) и `jobs.snapshot` (`GET /api/jobs/{id}`, ответ `POST /api/topics/{id}/run`)
  отдают поле `topic: <id>` (из `client = 'topic:<id>'`) любому читателю, независимо от
  `mine`; адрес ручных заданий не отдаётся (NFR-52). Сейчас `jobs.queue` отдаёт
  чужим заданиям только `status, position, mine, created, started, eta_start_s`, а
  `jobs.snapshot` поля клиента не содержит — задание темы в очереди неотличимо от чужого
  ручного, и подпись ожидания на стенде не построить. Дельта вносится в 06 §7.1 при DoR.
- Подписи интерфейса (прототип): «Прогон темы на автопилоте: после него — сравнение с
  прошлым и выпуск», «первый прогон темы», «статья не писалась: новых сигналов меньше
  порога (2)», «запущен вручную».

## 11. Открытые вопросы

- OQ-08.
- Снимать ли задание темы при паузе (E4): отмена `POST /api/jobs/{id}/cancel` (`OQ-12`
  закрыт, `8361a37`) допускает только адрес автора, у `topic:<id>` такого адреса нет;
  принято «не снимать».
- Становится ли отчёт прогона темы шагом ветки, если тема привязана к ветке (A5); принято
  «нет» до решения.
- `gone` без кандидата в исключённых нового отчёта — причина «не найдено в этом прогоне»
  или повторный поиск; принято первое.
- Прототип расходится с требованием (требование в силе): выпуск у первого прогона не
  исключён (A1); `gone` без `label` и с одной причиной «нет в этом прогоне» (шаг 5).
