## 2. Краткое описание

После постановки запроса аналитик видит честное ожидание: место в очереди и ожидаемое
начало, затем — прошедшее время, текущую стадию из 10 на полосе, поделённой по типичной
длительности («это не прогноз»), радар, на который по мере оценки ложатся кандидаты,
счётчики найденного, направления запроса и ленту вердиктов. Вкладку можно закрыть: ссылка
`#job=<id>` открывает то же ожидание в любой вкладке и восстанавливает картину разом. По
готовности экран сам переходит к отчёту; при отказе показывает причину и кнопку повтора.

## 3. Предусловия

- Есть задание с номером `<id>` (`jobs`), аналитик открыл `#job=<id>` (из UC-01 или по ссылке).
- API доступен.

## 4. Триггер

Переход на маршрут `#job=<id>` (`App.jsx`: `/^job=\d+/`).

## 5. Основной поток

1. Интерфейс показывает «Открываю запрос» (`appctx.jsx Loading`) и запрашивает снимок
   `GET /api/jobs/{id}` (`Wait.jsx`, один раз на номер).
2. Задание `queued` или `running`: интерфейс берёт из снимка `stage_typical` (медианы начала
   стадий по последним `jobs.HISTORY = 20` готовым заданиям) и `typical_run_s`, подставляет
   их в полосу (`timeline.js setTypical`: стадия без истории сохраняет константу, но не
   раньше предыдущей; длина полосы `TOTAL` становится `typical_run_s`, если он больше начала
   последней стадии, иначе начало последней стадии + 10 с) и показывает экран `Live`.
3. Шапка: статус с пульсом («В очереди» или «Идёт поиск сигналов»), текст запроса `h1`,
   кнопка «Ссылка на ожидание» (копирует адрес страницы без хэша — `location.href` до
   `#`, то есть с путём и строкой запроса, — плюс `#job=<id>`; тост «Ссылка на ожидание
   скопирована»). Полоса: часы «0:00» и «прошло, обычно около N мин» — одиночное значение,
   не диапазон (N = округлённое `typical_run_s`/60; пока готовых заданий нет —
   `jobs.DEFAULT_RUN_S = 1020` → «около 17 мин»), «этап n из 10» с названием стадии,
   10 сегментов, ширины которых пропорциональны интервалам `timeline.js STAGES` в масштабе
   `TOTAL` (по умолчанию 1140 с), подпись «Полоса поделена по типичной длительности этапов —
   это не прогноз.», кнопка «Все этапы» (раскрывает список 10 стадий; время начала стоит
   только у стадий, которые уже начались, у остальных пусто). Плитки: радар с лучом и подсказкой «Сектора появятся, когда
   модель раскроет запрос в направления», три счётчика («работ в корпусе», «заголовков о
   раундах и пилотах», «кандидатов к оценке») с «—», «Направления запроса» («Модель
   раскрывает запрос в направления…»), «Оценка зрелости» («Вердикты пойдут после сведения
   кандидатов…»).
4. Интерфейс запускает плеер `live.js watch(id)`: опрос `GET /api/jobs/{id}/events?after=<seq>`
   раз в `POLL_MS = 2500` мс; `elapsed` по часам сервера задаёт счётчик времени.
5. Пока задание `queued`: плеер после каждого опроса берёт снимок и шлёт синтетическое
   событие `queued`; экран показывает «В очереди: впереди N запросов и идущий, начнётся
   примерно через M мин» (при `position = 1` — «впереди идущий запрос, …»; M =
   округлённое `eta_start_s`/60, не меньше 1 — одиночное значение, не диапазон), подпись
   «Модель одна, запросы идут по очереди. Вкладку можно закрыть: ссылка сохранит место.»;
   опрос реже — `POLL_MS × 2`. `position` включает идущий, только если он есть, и снимок
   говорит об этом полем `running_ahead` (`jobs.snapshot`). Экран (`Wait.jsx queued`)
   вычитает идущий только при `running_ahead`. Без идущего (исполнитель ещё не забрал
   голову очереди) он пишет «впереди N запросов, начнётся примерно через M мин», а при
   пустой очереди — «впереди никого, начнётся в ближайшие секунды».
6. Статус стал `running`: плеер шлёт `running` (старт определяется по статусу, не по первому
   событию); экран — «Идёт поиск сигналов», часы идут, подпись полосы меняется на «Полоса
   поделена по типичной длительности этапов на последних прогонах — это не прогноз.»
   (`Wait.jsx start`; если экран открыт на уже идущем задании, остаётся подпись шага 3).
7. Приходят события прогона (контракт — UC-03 §10). Реакция экрана:
   - `stage` — «этап n из 10», название, сегмент активен, время начала в списке «Все этапы»;
   - `facets` — секторы радара (`facets_ru`, буквы А, Б, В…), чипы направлений, строка
     «Рынки: …» из `submarkets`; подсказка радара «Сектора — направления запроса; кандидаты
     появятся после сведения потоков»;
   - `counts` — счётчики с подписями: «в N названа технология», «N направлений», «снято как
     категория: N»; при `candidates` — россыпь кандидатов у края радара и подсказка
     «N кандидатов у края: по вердикту каждый встанет в пояс своей стадии или уйдёт за круг»;
   - `verdict` — точка кандидата в поясе своей стадии (класс `emerging`) или вне круга
     (прочие классы и `error`), запись ленты: значок ✓/✕, название (русское, если уже есть,
     иначе английский ярлык), причина без ссылок `[n]` (`noRefs`), штамп «сигнал» или
     `kind_label`; счётчик «N из M, сигналов X, снято Y»; лента показывает 6 последних,
     остальные — «Показать все N» / «Свернуть до шести последних» (без своей прокрутки);
   - `relevance` с оценкой < 2 — точка уходит за круг, счётчик сигналов уменьшается;
   - `top` — номера на точках по порядку ТОП, подсказка «Топ построен: номер — место по
     уверенности; дальше патенты и карточки»;
   - `card`, `titles` — английские ярлыки в ленте и на радаре подменяются русскими
     названиями (`BR-31`); названия не выдумываются заранее.
8. Статус стал `done`: плеер шлёт `done {report}`; экран показывает тост «Отчёт готов»
   (не при воспроизведении), обновляет историю и переходит на `#report=<name>` в виде
   радара (UC-04); вид передаётся в памяти вкладки (`navTo(..., { view: "radar" })`,
   `App.jsx nextOpts`), и экран отчёта сразу дописывает его в адрес (`Report.jsx
   reportHash`, `history.replaceState`) — `#report=<name>&view=radar`.

## 6. Альтернативные потоки и исключения

**A1. Задание уже готово (шаг 1).** Снимок `status = "done"` с `report` → интерфейс заменяет
адрес на `#report=<name>` (`history.replaceState`) и открывает отчёт в виде радара без
экрана ожидания; экран отчёта дописывает вид в адрес (`&view=radar`, как в шаге 8).

**A2. Переоткрытие ссылки в середине прогона (шаг 4).** Первая пачка событий после
открытия (> 1 события) помечается `replay = true`: счётчики выставляются без анимации,
точки ложатся разом, записи ленты без подсветки «fresh», тост «Отчёт готов» при
воспроизведении не показывается (`NFR-35`).

**A3. Исполнитель без событий стадий (шаг 7).** Статус `running`, но событий `stage` нет
(старый исполнитель или их запись падает): плеер берёт снимок и шлёт `progress {lines}` со
строками `jobs.progress`; экран показывает последнюю строку без префикса «N с ·» как
название стадии, подпись «примерно этап n из 10 (по времени)», стадия на полосе — оценка по
типичному времени, подпись «Подробных этапов нет: исполнитель стенда пишет только строки
прогресса. Текст — последняя из них, этап на полосе — оценка по типичному времени.»;
опрос — `POLL_MS × 2`. Первое же событие `stage` возвращает основной поток.

**A4. Дольше обычного (шаг 6–7).** Прошедшее время превысило `typical_run_s` из снимка
(без него — `timeline.js TOTAL = 1140`): статус «Идёт дольше обычного», полоса и статус
получают штриховку (класс `over`), подпись «Дольше обычного на M:SS: так бывает, когда в
живом поиске много источников.»; эта подпись перебивает подпись A3.

**A5. Нет связи (шаг 4).** Опрос не удался (сеть): плеер шлёт `offline`, статус «Нет связи с
сервером, повторяю» со штриховкой; пауза опроса удваивается от базовых `POLL_MS = 2500`
(`live.js`: `_wait = min(MAX_MS, _wait × 2)`), то есть первый повтор через 5 с, затем 10 и
20 с (`MAX_MS = 20000`); при первом удачном ответе — `online`, и статус возвращается к
тому, каким был бы без обрыва: «Идёт поиск сигналов», а после типичного времени — «Идёт
дольше обычного» со штриховкой (`NFR-08`, `NFR-24`). Пока связи нет, часы «дольше обычного»
статус не перебивают: «Нет связи» держится до `online`, подпись под полосой идёт дальше.

**A6. Воспроизведение после паузы вкладки.** Часы считаются от `elapsed` сервера плюс
время с последнего ответа (`live.js now()`), поэтому уснувшая вкладка не отстаёт.

**A7. Отмена автором (шаги 4–7).** Кнопка «Отменить» в шапке (рядом с «Ссылка на ожидание»,
нет после отказа E3) → своё окно подтверждения, а не `confirm` браузера (UX-16): «Отменить
запрос «<q>»?» и «Ожидающий уходит из очереди сразу, идущий остановится на границе этапа.
Отчёта по нему не будет.», кнопки «Продолжить ждать» (фокус по умолчанию, и Esc) и «Отменить
запрос» → `POST
/api/jobs/{id}/cancel`. Ожидающее получает `cancelled` сразу; идущее остаётся `running` с
`cancel = true` (снимок отдаёт `cancel`), кнопка — «Останавливается…» без нажатия, исполнитель
снимает задание на следующем событии `stage` (`save` не прерывается). Статус `cancelled` →
плеер шлёт `cancelled`: часы и полоса замирают, статус «Запрос отменён», подпись «Запрос
снят автором — отчёта по нему не будет.», луч гаснет, в шапке — «Новый запрос». Чужой адрес →
403, тост с текстом сервера «Задание поставлено с другого адреса — отменить его может только
автор.». Отменённое освобождает слот лимита 3/IP (`BR-35`). Отдельной отмены администратору
нет. Если процесс API остановился, пока идущее ждало границы стадии, при старте исполнителя
оно становится `cancelled`, а не возвращается в очередь (`jobs.requeue_stale`, `BR-40`).
Сторона исполнителя — UC-03 A11.

**E1. Задания нет (шаг 1).** `GET /api/jobs/{id}` → 404 «нет такого задания» → экран
`Fail` «Такого запроса нет» / «Ссылка устарела или набрана с ошибкой. Готовые отчёты — в
истории.». Иная ошибка — «Запрос не открылся» с текстом ошибки. Под текстом `Fail` — кнопки
«Новый запрос» (на главную) и «История» (`appctx.jsx Fail`).

**E2. Задание пропало во время опроса (шаг 4).** Опрос событий → 404 → событие `missing` →
экран «Такого запроса нет» / «Задание пропало из очереди. Задайте запрос заново.»

**E3. Отказ прогона (шаг 7).** Статус `failed`: плеер шлёт `failed {error, detail}`; часы и
полоса замирают там, где прогон остановился (`player.lastAt`); статус «Запрос не удался» со
штриховкой; под полосой — фраза `error` (если пуста — «Прогон остановился на внутренней
ошибке. Повторите запрос.»), кнопка «Повторить запрос» (повторная постановка того же
запроса — UC-01), и, если есть `error_detail`, раскрывающийся блок «Подробности» с сырым
текстом (`BR-42`); луч радара гаснет, подсказка «Прогон остановлен: отчёта по нему не будет».
Тексты `error` по типам отказа — UC-03 §6 (E1–E8).

**E4. Снято сторожем (шаг 7).** Частный случай E3: `error` = «прогресс не двигался N с —
задание снято сторожем» (UC-32).

## 7. Постусловия

- **Успех:** аналитик на `#report=<name>&view=radar`; история обновлена.
- **Отказ (E3, E4):** аналитик видит причину и может повторить; задание в `failed`.
- **E1, E2:** аналитик видит, что задания нет, и ссылку на историю.
- **A7:** задание в `cancelled`, слот адреса свободен, отчёта нет.
- Во всех случаях опрос остановлен при уходе с экрана (`player.pause()`).

## 8. Особые требования

- `NFR-08` (честное ожидание: «обычно около N мин» и «примерно через M мин» — одиночные
  значения, не диапазон; «не прогноз»; можно закрыть вкладку), `NFR-30`
  (опрос 2.5 с / 5 с), `NFR-35` (воспроизведение разом), `NFR-24` (офлайн с отступом
  5 → 10 → 20 с),
  `NFR-06` (лента без своей прокрутки: 6 последних), `NFR-10` (движение только от событий;
  счётчики без анимации при `reduceMotion`), `NFR-12` (ссылка на ожидание — адрес).
- `BR-31` (ярлык до русского названия), `BR-42` (две строки отказа), `BR-44` (копия стадий
  во фронте совпадает с `events.RUN_STAGES`), `BR-41` (сторож), `BR-35` (отменённое
  освобождает слот), `BR-40` (отменённое не возвращается в очередь при перезапуске).
- Отмена своего задания — FEAT-41 (A7).
- Контракт событий описан в UC-03 §10; здесь — только реакция экрана.
- Часы и полоса пишутся в DOM на `requestAnimationFrame`, без перерисовки React (комментарий
  `Wait.jsx`).
